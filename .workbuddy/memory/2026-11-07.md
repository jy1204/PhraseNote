## 保存短语后「先刷列表、再滚到修改位置」体验修复（前端）

- **根因**：保存/删除/追加成功后调 `loadDataFromDb(true, true)`，旧实现无条件
  `allPhraseList.value = []` 清空 → `.grammar` 高度塌缩、浏览器把 `scrollTop` 归零 →
  异步查库期间空白 → 第一页渲染时列表从顶部出现 → `finally` 里 `await nextTick()`
  （以及可能多轮 `await loadMore()` 跨帧）之后才把 `scrollTop` 滚回 `savedScrollTop`。
  这就是用户看到的"列表先刷出来、再跳到修改位置"。清空列表本身就是「需要事后恢复滚动」的原因。
- **改法**（`src/assets/js/PhrasePage.js`）：
  - `loadDataFromDb(force, preserveScroll, focusKeyword = '')` 加第三参数；
    `preserveScroll=true` 时**不清空列表、不开 loading 遮罩**，旧列表撑住高度与滚动位置，
    数据回来后按 `:key="item.id"` 做 keyed diff 原地替换（只有被改那条 id 变化需重建）。
    整个刷新没有可见中间态、位置全程不动。
  - `finally` 统一 `if (seq === loadSeq) loading.value = false`：原地刷新没开遮罩，
    但要替被抢占的旧加载收尾，避免 loading 永久为 true。
  - `restore()` 在 `nextTick` 同帧把 scrollTop 锁回；补分页 `while` 加
    `loadedCount` 增长校验 + 20 页上限（`loadMore` 被 loadingMore 守卫挡住时会死循环）。
  - 新增 `revealKeyword(wrap, keyword)`：改了关键词导致按 keyword 排序的位置变化时，
    在已加载页内找到该条，**瞬时**（非 smooth）滚到视口中央；已完整可见则完全不动。
    用 `rect 差值 + scrollTop - paddingTop` 算内容坐标（`.grammar` 是 grid 且无 position，
    `offsetTop` 参照物不对）。定位与 DOM 更新同帧完成，浏览器只绘制最终画面。
  - 调用点：编辑保存 `loadDataFromDb(true, true, savePayload.keyword)`；撞词追加
    `..., targetKeyword`；添加保存 / 删除仍只 `(true, true)`（添加时面板还开着，
    不额外滚动，否则关面板后位置莫名变化）。删除也顺带变成原地刷新、位置不动。
  - 换查询条件（切类型 / 搜索 / 导入导出）仍走 `preserveScroll=false`：
    清空 + 遮罩 + 回顶部，行为不变。
- **已知边界**：改关键词后若排序位置跑到未加载的页（如 apple→zoo），`findIndex` 返回 -1
  → 保持原滚动位置，不跨页翻找（避免拉全库 29 页）。
- **文档**《软件具体流程.md》551 → 561 行：4.1 补「loadDataFromDb 两种刷新模式」+
  历史跳动成因；4.2/4.3/4.4/4.5 的"刷新"改为"原地刷新"并标注 focusKeyword。
  围栏 42 个配对 OK。

## 去掉保存后所有主动滚动（用户反馈「变成快速滚动了，不想看见滚动」）

- **根因**：上一轮加的 `revealKeyword()` / `focusKeyword` 瞬时定位就是这个"快速滚动"。
  其可见性判断 `top + height <= cur + view` 在**词条高度超过视口**时恒不成立，
  于是每次编辑保存都会把列表瞬时滚到该条中央 → 明显的一下位移（用户形容为"快速滚动"）。
- 用户明确要求「不想看见滚动」→ **彻底删除** `revealKeyword()`、`loadDataFromDb` 第三参数
  及 finally 里的定位调用；编辑保存 / 撞词追加 / 删除 / 添加统一 `loadDataFromDb(true, true)`。
- `restore()` 保留但重新定性为「防漂移锁定」而非滚动定位：只在
  `Math.abs(scrollTop - target) > 1` 时才写回原值，正常情况完全不写（no-op）；
  用途是抵消浏览器 scroll anchoring / 内容高度变化对 scrollTop 的偷偷改动。
- **取舍**：改关键词后该条按 keyword 排序的位置变了，也不会滚过去找它 —— 保持原视野，
  列表位置一寸不动。若以后要"无滚动地定位"，只能改成不查库、用 savePayload 直接原地替换
  该条数据（有后端一致性风险，本轮未做）。
- 文档 561 → **563 行**：4.1 去掉 focusKeyword、补「全程不主动滚动」与历史三版演进；
  4.3 / 4.5 同步改为「不滚动、不定位」。围栏 42 个配对 OK。

## 最终方案：遮罩下滚完再显示（refreshMask）

- 用户三轮反馈串起来：①「先刷列表再滚动」体验差 → ② 改静默原地刷新+瞬时定位，
  用户说「变成快速滚动，不想看见滚动」→ ③ 全删定位后又问「**就不能滚动完成后再显示吗？**」。
  真实诉求是：**最终仍要停在修改的词条，但滚动过程必须不可见**（不是"不要滚动"）。
- **实现**：新增 `refreshMask`（`PhrasePage.js:75`），模板 `.content-knowledge` 内加
  `.pn-refresh-mask`（`PhrasePage.vue:51`），CSS 不透明层
  `position:absolute; inset:0; z-index:5; background:var(--pn-bg-app)`、**无淡入淡出**、
  带 CSS 转圈；`.search-keyword { position:relative; z-index:6 }` 让搜索框浮在遮罩上仍可见；
  `pointer-events:none` 不吞点击。
  - 选不透明覆盖层而不是 `display:none` / `opacity:0`：列表在遮罩下**照常布局、可写
    scrollTop、可量 rect**，定位计算完全不受影响。
- `loadDataFromDb(force, preserveScroll, focusKeyword)` 恢复第三参数：
  `masked = preserveScroll && !!focusKeyword` → 进函数先 `refreshMask=true`；
  finally 依次 `await nextTick() ×2`（等 `updateListFade` 的 paddingTop 落定）→
  `restore()` 防漂移 → 补分页 → `revealKeyword()` 定位 → **最后才 `refreshMask=false`**。
  撤遮罩**故意不加 seq 判断**，异常 / 请求被抢占也必须撤，避免遮罩卡死。
- **顺序铁律**：`restore()` 只能在定位之前调用 —— 它把 scrollTop 拉回 savedScrollTop，
  定位后再调会把目标位置覆盖掉。
- `revealKeyword` 修掉历史 bug：判断从「整条是否完整可见」改为「词条**顶部**是否已在
  视口内」；前者在 `height > view`（长词条）时恒不成立，导致每次保存都滚一下。
  长词条改为顶部对齐而非居中。
- 调用点：编辑保存 `focusKeyword=savePayload.keyword`（遮罩+定位）；撞词追加
  `targetKeyword`；添加保存 / 删除不带 focusKeyword → 静默原地刷新，连遮罩都不闪。
- 现在共三条刷新路径：换查询条件（清空+转圈+回顶部）／静默原地（添加删除）／
  遮罩下定位（编辑追加）。
- 文档 563 → **571 行**：4.1 改写为三条路径 + 三轮演进说明；4.3 / 4.5 同步；
  九章索引表加「保存后刷新 / 遮罩下定位」行。围栏 42 个配对 OK。

## base 屏蔽态改为「终态」（同日后续，用户："base只要状态变了就不动了"）

规格：`state=1` 一旦写入就是终态，之后任何路径都不再改动这一行。上一轮只处理了
读取侧「跳过查询」，写入侧仍有漏洞。

**最大漏洞**：`core/init.rs::run_migration` 逐条无条件
`UPDATE ... SET type,first_char,list,state=? WHERE source='base' AND keyword=?`，
且 `state = 有 user 行 ? 1 : 0` → 用户删掉的 base 词（无 user 行、state=1）在下次
基础库升级时被重置成 0「复活」；末尾清理多余 base 的 DELETE 也会删掉屏蔽行。

**改动（纯 Rust + 文档，前端与 db 文件未动）**：
- `init.rs::run_migration`：改查
  `SELECT COALESCE(state,0) FROM phrase_table WHERE source='base' AND keyword=? ORDER BY COALESCE(state,0) ASC LIMIT 1`；
  `Some(1)` → `continue`（不刷内容、不重置 state、也不 INSERT 出新的可见 base 行）；
  `Some(0)` → UPDATE 且 WHERE 带 `AND state=0`；`None` → 按种子 INSERT。
  清理 SQL 加 `AND state=0`，已屏蔽行原地保留。`ORDER BY state ASC` 兼容历史库

## 滑动窗口裁剪：解决「滚到底 2890 条全渲染」卡顿（纯前端）

用户问「一次性滚到底 2000 多个短语都加载了会不会卡，有没有更好办法」。
给三方案（A 滑动窗口裁剪 / B 完整虚拟滚动 / C 零风险滚动节流 + CSS 原生跳过渲染），
经 AskUserQuestion 用户选 **A（推荐）**。

**根因定性**（不是数据量，是 DOM + 每帧重排）：
- `PAGE_SIZE=100`，滚到底约 29 次 IPC；后端每次 `COUNT(*) FROM (UNION)` + OFFSET 深分页，
  索引后毫秒级，**不是瓶颈**。
- `PhrasePage.vue` 是 `.grammar` 里 `v-for` 全量平铺（每 keyword 一个 `.knowledge` +
  所有 `<p>` 短语 + 2 个 el-icon），无折叠/裁剪；2890 是关键词数，按每词 3 条估算
  约 1 万个 `<p>`、5 万级 DOM 节点、近 6000 个图标组件实例。
- 最致命：`onListScroll → updateListFade()` 每个滚动事件读 `scrollHeight/clientHeight/scrollTop`
  又立刻写 `marginTop/paddingTop`，节点多时每帧整树 layout thrashing。

**实现（JS + Vue + CSS，Rust / db 未动）**：
- 常量 `MAX_RENDER=300`、`TRIM_STEP=100`；`aboveCount = loadedCount - allPhraseList.length`
  （= windowStart，响应式化供模板显示提示条）。
- `trimHead(wrap)`：`loadMore` 后（视口必在末尾）裁头部最远一页，`windowStart += cut`、
  `loadedCount` 不变；**复用 loadPrev 的 rect 差值补偿** —— 记录裁剪后将成为第 0 条的
  keyed 节点，nextTick 后把它的视觉位移补回 scrollTop，提示条出现/消失、卡片高度不固定
  都自动算进去，无需测高度。`.grammar` 加 `overflow-anchor:none` 防浏览器双重补偿。
- `trimTail()`：`loadPrev` 后（视口必在开头）裁尾部一页，`loadedCount = windowStart + len`
  重算，被裁尾部变「未加载」，往下滚会取回；不动 scrollTop。
- 恒等式 `loadedCount = windowStart + 数组长度` 全程保持，数据连续不重不漏。
- `onListScroll` 改 **rAF 节流**（一帧一次）；`updateListFade` 只在样式值真变化时才写；
  `onUnmounted` cancel rAF。
- `fetchPage(offset, limit = PAGE_SIZE)`；`keepWindow` 原地刷新一次取 `MAX_RENDER` 条，
  避免 while 补页连发 IPC；补页用 `loadMore(false)` **禁止裁剪**（否则 windowStart 变、
  restore/revealKeyword 基准错），定位完成后再 while `trimHead` 收敛回 300。
- 模板加 `.pn-window-hint`（`v-if="aboveCount>0"`，固定 36px，`.knowledge` 之外，
  不影响 `querySelectorAll('.knowledge')[idx]` 定位）；CSS 关锚定 + 提示条样式。

**取舍**：滚动条只代表当前窗口（与既有居中窗口语义一致），**不用等高占位** —— 等高占位
在快速拖滚动条时会露出大片空白且需按 offset 重建窗口。若以后要「滚动条代表全量 +
任意跳转」，才上完整虚拟列表（动态高度测量 + offset 重建 + 重写定位函数）。

**验证**：`npx vite build` 两次通过（2.14s / 3.76s）。Python 状态机模拟 2890 条：
滚到底 → windowStart=2590 / dom=300 / loadedCount=2890；回滚到顶 → 0/300/300；
再滚 12 页 → 1200/300/1500；补页不裁剪 → dom=600 且 windowStart 不变 → 收敛后
1500/300/1800，恒等式与数据连续性全部断言通过（ALL_OK）。
